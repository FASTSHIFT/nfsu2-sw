# 12 - RK3566 板子移植与排障复盘
> 日期：2026-10-17。前置：[11 OpenUG2 移植评估](11-OpenUG2移植评估.md)、[02 R36S 性能分析](02-R36S性能分析与优化方案.md)、[10 draw 合并重做](10-draw合并重做.md)。
> 结论先行：同一个 Xbox 重编译二进制（md5 `0ac092afbc44`）搬到 RK3566（立创泰山派）上，干净测量的中位帧时间是 **84.8 ms（约 11.8 fps）**，R36S 同场景是 114~125 ms（约 8 fps）。过程中一次「2.8 fps、81 °C」的测量是我自己的测试方法出错（同时跑了 5 个游戏实例），不是板子的问题。这块板子上瓶颈已经从 guest 主线程/执行器移到了 GL 线程。

## 1. 背景与目标
用户有一块 RK3566 开发板，也在考虑 X35S 这类 RK3566 掌机：CPU 是 A55 而不是 A35，GPU 是 Mali-G52，资料上写支持 Vulkan，价格和 R36S 差不多。要回答的问题是：换这个 SoC，Xbox 版能快多少、值不值得适配 Vulkan。

## 3. 时间线与每一步的真实原因
### 3.1 「GPU 是坏的」：eglInitialize 失败
- 现象：`eglinfo`、`es2_info` 都报 `eglInitialize failed`，`glxinfo` 渲染器是 llvmpipe。
- 我最初的推测是用户态 libmali（g2p0）与内核 DDK（g7p1）版本不匹配，**这个推测是错的**。
- 用 strace 看：kbase 的 `/dev/mali0` 打开和 ioctl 都成功，失败发生在 X11 平台初始化——libmali 向 Xorg 发 `DRI2Connect`，返回的设备名是空字符串，随后 `open("")` 报 ENOENT。也就是 Xorg 的 modesetting 驱动没有给 DRI2 提供设备，EGL 的 **X11 路径**不通。
- 我写了最小 GBM+EGL 探针（`gbm_create_device` + `eglGetPlatformDisplayEXT(EGL_PLATFORM_GBM_KHR)`），在同一个 libmali 上直接成功：`EGL 1.4 vendor=ARM`、`GL_RENDERER=Mali-G52`、`OpenGL ES 3.2`，有 ASTC，无 S3TC（与 R36S 相同）。
- 结论：不需要换 libmali。我们的游戏本来就走 SDL KMSDRM（即 GBM），与 X11 无关。运行时要先停掉 lightdm，释放 DRM master。

### 3.2 SDL 没有 KMSDRM
- 板子自带两个 SDL：Ubuntu 的 2.0.10（视频驱动里没有 KMSDRM）和 `/usr/local` 的 2.30.10（驱动列表是 `x11 wayland offscreen dummy evdev`）。后者 `strings` 里能搜到 `KMSDRM_bootstrap`，但那只是符号，实际没编进去。游戏日志里是 `[GL] SDL video: kmsdrm not available`。
- 解法：在 `ug2-r36s-cross:focal` 镜像里从 Ubuntu 的源码交叉编译 SDL 2.0.10，开启 KMSDRM、ALSA、libudev。configure 的几个坑：
  1. `libdrm`/`gbm` 的 pkg-config 要指到解包出来的 stage 目录（`PKG_CONFIG_LIBDIR` + `PKG_CONFIG_SYSROOT_DIR`），否则静默关闭 KMSDRM。
  2. `EGL support` 检测失败，原因是 `eglplatform.h` 要 `X11/Xlib.h`；放一个只有 typedef 的桩头文件就过了（`-DMESA_EGL_NO_X11_HEADERS` 对检测无效）。
  3. ALSA 检测靠链接 `-lasound`，必须给 `LDFLAGS=-L<stage>/usr/lib/aarch64-linux-gnu`，否则静默只剩 `dummy oss`。
  4. 不开 libudev 的话，SDL 2.0.10 的 evdev 不会枚举任何输入设备（见 §6）。
- 分辨率：SDL 2.0.10 的 KMSDRM 用 CRTC 当前模式，电视会落到首选的 4K30。我给 `SDL_kmsdrmvideo.c` 加了环境变量 `SDL_KMSDRM_MODE=WxH`，在连接器的模式表里选对应分辨率（`sdl-kmsdrm-mode.patch`）。默认用 640x480，与 R36S 面板一致。

### 3.3 一次错误的性能结论（本次最大的教训）
- 现象：第一次能出画面的测量是 **2.8 fps、帧时间 400~560 ms**，SoC 81 °C，我还据此怀疑过 GPU 一直在 200 MHz、内存控制器频率低，并手动改了 governor。
- 真实原因：板子上**同时有 5 个游戏实例在跑**（`ps` 显示 etime 从 33 分钟到 2 分钟，负载 12）。
  - `timeout 300 ./nfsu2_recomp` 发的是 SIGTERM，游戏不理会，实例一直不退出。
  - 我多次覆盖正在运行的 `run.sh`。bash 是边读边执行脚本的，文件被改写后会按旧偏移在新内容里继续执行，又多拉起了新的实例。
  - 中间还有一个被 strace 包着的实例没有退出。
- 症状里最有迷惑性的是 `[frame]` 行的 `wait=270 ms`：它的含义是「GL 线程在等游戏线程」（`gl_ms = frame - swap - wait`），GL 线程本身只忙 100 ms 左右，真正的问题是多个实例互相抢 CPU/GPU。
- 修正：`timeout -s KILL`；`run.sh` 不再在运行中被覆盖；测量前先 `ps` 确认没有残留实例。
- 另一个同类坑：在远程 shell 里 `pkill -f`/`pgrep -f` 的模式串本身就出现在这个 shell 的命令行里，会把自己的 SSH 会话杀掉（本次出现过多次，包括一次把 docker build 的 SSH 命令自己杀掉）。改成按 PID 杀。

### 3.4 干净重测
条件：640x480，`RECOMP_KMS_PRESENT=1`、`RECOMP_GL_THREAD=1`、`RECOMP_FRAME_LAG=1`、`RECOMP_GUEST_ONE_CORE=1`（与 R36S 启动脚本同一组），GPU/dmc governor 设为 performance，rain/道路反射关闭（二进制内置的质量默认值），跳过进入比赛前的 150 帧，共 1168 帧：

| 指标 | RK3566 | R36S（docs/02、docs/10 基线） |
|---|---|---|
| 帧时间 p10 / 中位 / p90 | 80.7 / **84.8** / 101.5 ms | 114~125 ms |
| GL 线程忙 / swap / wait（均值） | 63.3 / 25.4 / 0.0 ms | GL 约 94% 忙 |
| draw/帧 | 约 2280 | 约 2050~2300 |
| 线程占用 | GL 75%，主线程 47~51%，执行器 47~49%，混音线程 11% | 主线程与执行器各约 87~90% |
| 温度（SoC / GPU） | 41~46 / 40~45 °C | 70~81 °C（docs/gpubench 的 glmark2 期间，不是同一负载） |
| 频率 | CPU 1.8 GHz，GPU 800 MHz，dmc 1056 MHz | CPU 限 1.2 GHz |

对比时要注意：R36S 的启动脚本把 CPU 限到 1.2 GHz 做温控，这块板子没限；两者开了不同的 governor 配置。用户后来加了风扇，反馈「流畅不少」，那是主观感受，我没有在加风扇后重测。

**关键推断（未做对照实验）**：R36S 上是 guest 主线程和执行器饱和（xtrace：GL 空闲时帧时间仍有 90 ms），这块板子上它们只有约 50%，GL 线程到了 75% 且 `wait=0`。也就是说 A55 把 CPU 侧的瓶颈卸掉后，瓶颈移到了 Mali 侧的提交和填充。这意味着在 RK3566 上，减少 draw call 或片元工作的优化（合批、剔除）会比在 R36S 上更值钱。这是从线程占用推出来的，没有用 `EXP_RD`/`EXP_DROPFRAG` 那类旋钮验证。

## 4. 基础性能基准（排除「板子本身有问题」）
| 测试 | RK3566 结果 | 备注 |
|---|---|---|
| CoreMark 单线程 | 7849（约 4.36/MHz） | A55 常见水平 |
| CoreMark 4 线程 | 31254 | 约 4 倍，线性 |
| 依赖链整数循环 | 3.3 ns/iter | 与 1.8 GHz 吻合，没有降频 |
| memcpy 64 MB / memset 64 MB | 约 2.4 GB/s / 约 6.7 GB/s | dmc 324 MHz 与 1056 MHz 单线程差别很小 |
| memcpy 32 KB（L1） | 约 12 GB/s | |
| drawbench「nv2a-like」每 draw CPU 开销 | **16.7 µs** | R36S 23.5~25.2 µs |
| 填充（4 个全屏贴图 quad + glFinish） | 2.13 ms / 577 Mpix/s | R36S 2.2~2.3 ms / 530~556 Mpix/s |
| `glClear + glFinish` 往返 | **1.30 ms** | R36S 0.16~0.23 ms |

- 每 draw 的驱动开销只比 R36S 低约 30%，没有数量级差别：Mali 闭源驱动的提交成本在两个 SoC 上是同一个量级。
- 填充测试里这块板子几乎没有比 R36S 快，但它被 1.3 ms 的同步往返延迟主导，不能据此判断 G52 的真实填充能力。往返延迟高很多，可能和用户态 g2p0 与内核 g7p1 混搭有关，**这只是猜测，没验证**。
- `glmark2-es2-drm --off-screen` 在这个 libmali 上 `eglCreateWindowSurface` 报 `0x3009`（EGL_BAD_MATCH），换几种 visual-config 都一样；X11 版因 §3.1 的 DRI2 问题不能用。所以没有 glmark2 分数，改用 `drawbench`（需要一个补丁，见 §8）。
- `drawbench` 原版用 `eglGetDisplay(gbm)`，这个 libmali 不会据此选 GBM 平台，要改用 `eglGetPlatformDisplayEXT(EGL_PLATFORM_GBM_KHR, ...)`。

## 5. Vulkan
- 这个镜像上 Mali 没有 Vulkan：`libmali.so` 里没有任何 `vk*` 符号；系统 Vulkan ICD 只有 lvp（软件）、broadcom、radeon；Mesa 是 21.2.6，内核 4.19 也没有 panfrost DRM，所以 PanVK 用不了。
- 要用 PanVK 需要主线内核加新版 Mesa，而且我之前查到 PanVK 的 1.1 一致性认证是 G610，G52 不在其中。
- 我们仓库里 `VULKAN_NOTES.md` 记录 Switch 上的 Vulkan 渲染器「比赛帧率与 GL 版差不多」，原因是 GL 版本来就卡在游戏主线程和执行器。**但在 RK3566 上瓶颈已经变成 GL 线程**，这个结论不一定还成立，Vulkan 的每 draw 开销降低在这里才可能有收益。现在没有可用的 Vulkan 驱动，无法验证。

## 6. 键盘
- 现象：用户反馈键盘没反应。
- 原因 1：我从 R36S 启动脚本抄来了 `RECOMP_KEYBOARD=0`（R36S 用手柄），键盘映射被关掉了。改为 `1`。游戏自带的映射（`src/input/xinput_device.c`）：方向键 = 十字键，Enter = A/开始，Esc = BACK，W/S = RT/LT（油门/刹车），A/D = 左摇杆，Space = B，Ctrl = Y，Shift = 白键，Q = 黑键。
- 原因 2：SDL 编译时关了 libudev。SDL 2.0.10 的 evdev 只通过 udev 枚举设备，不开 libudev 就一个键盘都看不到。重编后开启（运行时 `dlopen libudev.so.1`）。
- 原因 3：`/dev/input/event*` 属于 `input` 组，`lckfb` 不在里面。已执行 `usermod -aG input lckfb`（**持久的系统改动**）。
- 验证：用 uinput 虚拟键盘注入 W/A/Enter/Space/Esc，SDL 测试程序收到全部 10 个事件；游戏进程打开了 7 个 `/dev/input/event*`。实体键盘按键是否在游戏里生效，由用户确认（测试 OK）。

## 7. HDMI 声音
- SDL 的 ALSA 驱动当时没编进去（原因见 §3.2 第 3 条），日志是 `[AUDIO] SDL audio init failed: Audio target 'alsa' not available`，游戏随后回退到 waveOut 也失败，实际一直没声音。这个失败在第一次干净重测里就已经存在，我当时没留意。
- 修复后 `AUDIODEV=plughw:1,0`（HDMI 是 card 1，`plughw` 负责速率/格式转换）。
- 又遇到一次 `ALSA: Couldn't open audio device: Device or resource busy`：用户会话里的 PulseAudio 偶尔占着 HDMI 的 PCM。启动脚本在运行前 `pactl suspend-sink 0 1; pactl suspend-sink 1 1`，退出时恢复。
- 验证：日志 `[AUDIO] SDL alsa output: 48000 Hz, 2 ch`；`/proc/asound/card1/pcm0p/sub0/status` 为 `RUNNING`，`hw_params` 为 S16_LE / 48000 / 2 声道。喇叭实际出声由用户确认（测试 OK）。

## 8. 复现
文件：
- `r36s/rk3566_run.sh`：板子上的启动脚本（放到 `/userdata/nfs8/run.sh`）。会停 lightdm 并保证退出时恢复；`GOV=0` 保留默认 governor；`MASH=1` 让游戏自己按 A/Start 进入比赛做测量；`MODE=WxH` 改分辨率；`AUDIODEV` 改声卡；每 15 秒记录频率、温度和线程占用（配合 `thr.sh`）。
- `tools/rk3566/`：`fetch_sdl_deps.sh`（下载 arm64 的 -dev deb 和 SDL 源码）、`build_sdl.sh`（docker 里交叉编译）、`sdl-kmsdrm-mode.patch`、`sdl_input_test.c`（SDL 键盘事件探针）、`inject_kbd.c`（uinput 虚拟键盘）、`thr.sh`、`drawbench-gbm-platform.patch`（给 `r36s-tools/gpubench/drawbench.c` 的补丁）。

步骤：
1. `fetch_sdl_deps.sh` → 解包源码 → 打补丁 → `build_sdl.sh`，得到 `libSDL2-2.0.so.0.10.0`，放到板子 `/userdata/nfs8/lib/`。
2. 游戏数据（`build/game`，2.5 GB）用 `tar -chf - … | ssh … 'tar -x --skip-old-files'` 传到 `/userdata/nfs8/game`，用 `find -printf '%P %s'` 逐项核对（193 个文件大小一致）。WiFi 约 2.4 MB/s，约 17 分钟，中断可续传。二进制用 `build-r36s/nfsu2_recomp`（与 R36S 同一个 md5）。
3. `ssh lckfb@host 'cd /userdata/nfs8 && ./run.sh 3600'` 玩；`MASH=1 ./run.sh 200` 做测量。

## 9. 方法上的复盘
1. **先确认环境干净再测量。** 本次 80% 的弯路来自「板子上到底有几个实例」。测量前固定做 `ps`，脚本里用 `timeout -s KILL`，不要在脚本运行时覆盖它。
2. **不要把没验证的推测写成原因。** 「libmali 与内核版本不匹配」我说得很肯定，strace 一跑就是另一层的问题。看症状时先抓最底层的证据（系统调用、日志行），再下结论。
3. **日志字段的含义要先查源码。** `wait` 是 GL 线程在等游戏线程，不是「等 GPU」；看反了会把调查方向引到 GPU 频率上。
4. **留意后台静默失败。** 音频初始化失败的那行日志早就在第一次干净运行里，只是当时只盯着帧率。
5. **对照对象要同条件。** R36S 限了 1.2 GHz、板子没限；两者 governor 不同；这块板子有没有风扇也会影响。表里的比值只能当量级，不是严格的 SoC 对比。

## 10. 未验证与后续
- 默认 governor（`GOV=0`，`simple_ondemand`）下的帧时间；性能 governor 对结果的贡献没有拆开。
- 长时间游玩的温度曲线（只测了 200 秒；加风扇前后没有对照）。
- `glClear+glFinish` 1.3 ms 往返延迟的原因，以及换匹配的 libmali 版本后的变化。
- 用 `EXP_RD`/`EXP_DROPFRAG` 在这块板子上做一次与 R36S 相同的 GL 线程拆分（固定/每 draw/片元），验证「瓶颈已移到 GL 线程」的推断。
- 在这块板子上试 640x480 以外的分辨率（720p、1080p）看填充能走多远。
- 退出游戏目前只能超时或杀进程，Esc 是游戏内的 BACK。
