# 10 - draw 合并重做：基线与方案

> 日期：2026-10-08。前置：[09 碎片 draw 合并尝试](09-碎片draw合并尝试.md)（旧方案，已回退）、[07 RenderDoc 帧捕获分析](07-RenderDoc帧捕获分析.md)。

## 1. 为什么回退旧方案

旧方案（提交 6dbb731）在顶点着色器里按 `gl_VertexID` 选常量块：每个顶点跑一个循环，再动态索引 `c[blk*192+i]`。PC 上 draw 减 76%、画面正确，R36S 上从 7-13 fps 掉到 0.2-2.5 fps。问题在方案本身：

- 改的是 shader，代价在 Mali 上完全不同于 llvmpipe，PC 验证不能推断真机；
- Mali 的 uniform 预算只够 5 块，合并率 1.45（PC 4.2），省不下多少；
- 每个 draw 都做 `mg_match`/`vertex_runs` 扫描，合并不成功时纯亏 CPU。

代码已 revert，`docs/09` 留作失败分析。默认行为不变（回退前后基线一致，见下）。

## 2. 基线（PC，llvmpipe，回退后）

工具：`RECOMP_PERF_LOG=2` 每帧一行 `[frame] n ms gl wait swap dc frag calls`，与 `[AUTOTEST] HUD live` 在同一日志流里，可以并排看比赛开始前后。`frag` = 索引数 < 50 的 draw。

```bash
BIN=$PWD/build/linux-hud/nfsu2_recomp HUD_STOP=12 RECOMP_SKIP_INTRO=1 \
  RECOMP_PERF_LOG=2 bash tools/pc/run.sh base 150
```

HUD 首次更新后各阶段（`build/base0`，每帧中位数）：

| 阶段 | 帧 | dc | frag | calls | ms |
|---|---|---|---|---|---|
| HUD 已创建，仍是加载/菜单画面 | 0-59 | 161 | 161 | 1542 | 38.7 |
| 赛前场景 | 80-209 | 1067 | 557 | 11729 | 40.2 |
| **比赛** | 225+ | **2531** | **1475** | **25621** | 44.1 |

要点：

- HUD 在 3D 场景出现前约 70 帧就开始更新（Player 构造时创建 HUD），所以 `HUD live` 是"进比赛流程"，稳态基线要从它之后约 220 帧起取。
- 比赛里 **58% 的 draw 是碎片**，平均每个 draw 约 10 次 GL 调用。
- `wait=0.0`：llvmpipe 下 GL 线程一直满载，PC 上看不出游戏线程是不是瓶颈。

## 3. R36S 基线（真机，2026-10-09）

```bash
R36S_HOST=192.168.10.241 python3 r36s/autotest.py --baseline   # 部署 + 进比赛 + 取数 + 热键退出
```

driver 的 `baseline` 模式：启动游戏，临时给 env.txt 加 `RECOMP_PAD_MASH=200,100,7` 和 `RECOMP_PERF_LOG=2`（跑完还原），等日志出现 `HUD live`，再收 420 帧 `[frame]`，在设备上汇总后 SELECT+START 退出。**菜单操作和 PC 完全相同**（游戏进程内连按，不再由 driver 通过 evdev 点 A）。进比赛 22.8 s，整个流程 80 s。

设备环境：`env.txt` 里 `RECOMP_GL_SKIP=320x240,128x128`（路面反射和车体环境贴图关闭），CPU 被限到 1200 MHz，结束时温度 72 C。

稳态（HUD 后第 335 帧起的 100 帧，中位数）：

| 指标 | 值 |
|---|---|
| 帧时间 | **125.2 ms**（约 8 fps，范围 106-236） |
| GL 线程忙 | 123.8 ms |
| WAIT（GL 等游戏线程） | 0.0 ms |
| draw / 碎片 draw | 2301 / 1430（**62%**） |
| GL 调用 | 15864（约 6.9 次/draw） |

30 帧窗口（HUD 后）：加载画面 161 draw、帧时间 45 ms，其中 WAIT 约 35 ms（游戏线程慢）；第 90 帧起 3D 场景出现，`WAIT` 降到 0，GL 线程满载；约第 240 帧后进入稳态。

结论与限制：

- 比赛里 GL 线程满载（`WAIT`=0），菜单/加载阶段则是游戏线程慢（`WAIT` 约 35 ms）。
- `GL` 是"帧时间 - WAIT - SWAP"，包含 GL 线程在驱动里等 GPU 的时间，所以单看它分不清提交开销和 GPU 负载。下一节用实验拆开。
- 取样要按场景，不能按帧号：HUD 出现后依次是加载（约 160 draw）、赛前场景（非碎片 draw 约 290）、比赛场景（约 870），各段时长每次不同。driver 现在以"非碎片 draw ≥ 600"判定比赛场景，跳过前 120 帧（比赛场景开头约 100 帧更重：dc 2300 -> 2670 -> 2290，帧时间 125 -> 170 -> 122 ms），再取 100 帧。（早期用"最后 100 帧"的两次结果，有一次落在赛前场景，那一次和随后的 dropfrag 对比无效。）

## 3.1 拆分实验（真机，比赛场景稳态，中位数）

开关在 `nv2a_gl.c`（只用于实验，会改画面）：`RECOMP_GL_EXP_DROPFRAG=1` 跳过索引 < 50 的 draw；`RECOMP_GL_EXP_RD=2` 每个 draw 周围开 `GL_RASTERIZER_DISCARD`（顶点和提交都在，片元全无）；`RECOMP_GL_EXP_RD=1` 是对照（只多两个调用）。

```bash
R36S_HOST=192.168.10.241 r36s/exp.sh base dropfrag:RECOMP_GL_EXP_DROPFRAG=1 \
    rd:RECOMP_GL_EXP_RD=2 both:RECOMP_GL_EXP_DROPFRAG=1,RECOMP_GL_EXP_RD=2
```

| 实验 | 帧时间 | GL 线程忙 | WAIT | draw | GL 调用 |
|---|---|---|---|---|---|
| base（4 次：123.8 / 125.2 / 120.0(对照) / 123.3） | 123.3 | **121.7** | 0 | 2214 | 15325 |
| 去碎片 draw | 103.9 | 59.9 | 45.0 | 846 | 6473 |
| 关光栅化 | 103.3 | 59.4 | 42.0 | 2222 | 19855 |
| 两者都做 | 111.9 | **32.4** | 78.1 | 869 | 8292 |

按 `GL = 固定 + 每 draw 提交 × draw 数 + 片元` 解：

- 关光栅化后留下的是固定 + 提交：59.4（全部 draw）与 32.4（只剩 846 个）之差 27 ms 来自 1368 个碎片 draw，约 **20 us/draw**。
- 固定部分约 **16 ms**（清屏、拷贝、present、队列）。
- 提交总计 20 us × 2214 ≈ **44 ms**，其中碎片 draw 占约 27 ms。
- 片元（光栅化）= 122 - 16 - 44 ≈ **62 ms**，其中碎片 draw 约 35 ms，其余 27 ms。

所以 122 ms 的 GL 线程帧约为：固定 16 + 提交 44 + 片元 62。这是线性模型，`rd` 多出的两个调用约 1-3 ms（对照组 120.0 与基线 123.8 无显著差异）。

**上限分析**：

- 合并碎片 draw 最多省提交 ~27 ms（实际约 20 ms），GL 线程 122 -> ~100 ms。
- 但后两组 `WAIT` 为 42-78 ms，GL 线程已经在等：**上游（游戏线程 + 执行器）每帧约 104-112 ms**，是下一个下限。合并 draw 的帧时间收益上限是 123 -> 约 105-110 ms（约 -12%），再往下要动上游。
- 片元 62 ms 是 GL 线程里最大的一块，合并 draw 碰不到。
- 去碎片 draw 的截图：路面变黑、HUD/路灯/招牌消失，车和大楼还在。路面和 HUD 就是被拼成碎片的。

## 4. 方案候选与优先级

按上面的拆分重排：

| # | 方向 | 对 GL 线程 | 说明 |
|---|---|---|---|
| 1 | 找出 62 ms 片元里谁最贵 | 最大一块 | 按 surface/pass 分别开关光栅化（每个 pass 一次实验），找出后处理、半透明、路面等的成本；分辨率/pass 裁剪不动 shader |
| 2 | 上游 ~105-110 ms | 决定下限 | GL 线程降到 100 以下之后，帧时间由游戏线程 + 执行器决定（docs/04 §8）。不动它，其他优化的收益被封顶 |
| 3 | 合并碎片 draw | 最多 -20 ms | 先做不改 shader 的版本（相同常量的相邻 draw，或 CPU 预变换）；改 shader 的方案必须先在真机验证 |
| 4 | 减冗余 GL 调用 | 小 | 比赛里 15k 调用 / 2.2k draw ≈ 7 次/draw，提交 20 us/draw，值得统计但上限有限 |

下一步先做 1（实验成本最低，收益最大），并同时看上游为何是 105 ms。

## 5. 一次启动里切换 knob：sweep（2026-10-13）

反复重启游戏既慢又引入漂移，所以实验都改成运行时切换：

```bash
R36S_HOST=192.168.10.241 python3 r36s/autotest.py --sweep \
    --set rd:EXP_RD=2 --set drop:EXP_DROPFRAG=1 \
    --set spec:POKE_VA=3773600,POKE_VAL=0,RESTORE=1      # POKE 的原值写在 RESTORE
```

- 只启动一次；进比赛场景并稳定后，按 `B S1 B S2 B ...` 的顺序切换 `/tmp/nfsu2.knobs`，每个窗口 40 帧稳定 + 80 帧取样。每个设置和它前后两个基线的均值比（`d_ms` 等），窗口之间的漂移被抵消。
- 每个窗口同时记温度、CPU/GPU 频率和一张截图（设备上算亮度判黑屏，非黑才拉回；有 PIL 时还会算与基线截图的像素差，路面带 `d_road`、全画面 `d_all`）。
- knob（`knobs.h`）：`EXP_DROPFRAG`、`EXP_RD`、`EXP_RDSEL`、`EXP_QUERY`、`POKE_VA/POKE_VAL`、`DUMP_DRAWS`。

## 6. 默认关闭下雨和道路反射

`src/main.c quality_defaults()` 在启动时给 `RECOMP_POKE` 加默认项，CMake 选项 `NFSU2_RAIN` / `NFSU2_ROAD_REFLECTION` 默认 OFF，运行时 `RECOMP_RAIN=1`、`RECOMP_ROAD_REFLECTION=1` 可恢复。日志有一行 `[quality] RECOMP_POKE=...`。

| 地址 | 值 | 含义 | 效果（真机，一次启动内切换） |
|---|---|---|---|
| `0x3A3FA0` | 0 | `PrecipitationEnable`（`Rain::UpdateAndRender` = Xbox `sub_0020A570` = GC `0x802532B0`）：雨强度强制 0，雨的绘制直接返回 | 下雨时帧 188 ms -> 132 ms，draw -1100 左右 |
| `0x3994A0` | 0 | `EnableRoadSpecular`：道路反射 pass | draw 2131 -> 1962 (-8%)，画面无可见变化 |
| `0x3CC5E8` | 0 | `DrawCarsReflections` | 画面无可见变化 |

走过的弯路：先戳的 `0x45B004`（`IsRainingAt` 的 `Chance100`，GC 里从不被写）只管"按世界时间自动下雨"，赛道设定的雨它管不到；`BaseDampness`/`SetUberRoadDampness`（`0x3CD9F8/0x3CD9FC`）、`0x3CDA00`、`0x3CDA08` 清零后路面像素变化 < 1.5%。**下雨会让一局里的基线从 122 ms 跳到 188 ms，是之前 sweep 数据漂移的原因**，所以这两项必须默认关。

## 7. 视锥剔除生效吗

`EXP_QUERY=1`：下一整帧每个 draw 先在"关背面剔除/深度/模板/颜色写入"下发一次 `ANY_SAMPLES_PASSED` 查询，数没有任何像素的 draw（PC，起跑线，约 2500 draw）：

| 渲染分辨率 | 零像素 draw | 占索引 |
|---|---|---|
| 1x | 约 13%（330 个） | 11% |
| 3x（像素 9 倍） | 5%（120 个） | 7% |

差值约 8%（210 个 draw）是小到不覆盖像素中心的亚像素物体，剩下 5% 才是视野外或退化的 draw。结论：**视锥剔除生效**，剔除这条路上最多再拿 5-13% 的 draw。`culldiv` 只用在车身部件剔除平面里，不是场景的按尺寸剔除。

## 9. 一帧的构成：RenderDoc 抓帧分析（2026-10-14）

资料：`trace/nfs8.rdc`（PC，llvmpipe，2026-10-06 的比赛起跑线帧，2400 个 draw；抓的时候的画质开关状态没有记录，里面带 128x128 / 320x240 的环境贴图和反射 pass，所以不是关了道路反射的状态）。脚本在 `tools/rdc/`。

### 9.1 怎么分析才不慢

- **别对每个 draw 调 `SetFrameEvent`。** 它每次要把软件 GL 从帧头重放到该事件：同一个 rdc 上，重放到 eid 2000 约 1.5 s，到 eid 16000 约 13 s，2400 个 draw 逐个取状态就是几十分钟。
- 固定成本：打开重放 16 s（llvmpipe 加载）。之后**一次**重放拿全部计数器 15 s（`rd_counters.py`），**一次**重放导出一批纹理 17 s（34 张，`rd_textures.py`），**一次**重放取少数几个时间点的颜色缓冲（`rd_progress.py`，每点 2-13 s）。
- 状态不用重放：从 `renderdoccmd convert -c xml` 的调用流里按顺序跟踪 GL 状态（program、纹理、FBO、blend、常量），2.6 s 解完 2400 个 draw（`draw_anatomy.py`）。注意 `glUniform4fv` 的参数名是 `values`（`<array>`），不是 `value`；顶点/索引的字节不在 XML 里，只有 `glUnmapBuffer` 的偏移和长度，字节要靠重放里的 `GetBufferData`（`rd_meshhash.py`，每个 draw 约 2 s，只对挑出来的几个做）。
- qrenderdoc 的 Python 要用 `qrenderdoc --python x.py`（自带 `renderdoc` 模块，版本 1.46），脚本结尾用 `os._exit(0)` 退出，参数走环境变量。

### 9.3 纹理看图确认的类别

34 张纹理（program 156/153 里最常用的）按目视分成：植被（431 草丛、499/613 松树、656/657 花、655 蕨、501/498 枝叶）、建筑立面（469/468 混凝土、470 砖、560/523 窗、484/442/500/370 墙面）、路面（471 鹅卵石、457/497 沥青、441、569）、灯光（421/490 光晕、462/571/572 霓虹、527 月亮）。

### 9.4 为什么是几百到上千个碎 draw：重复的模块，不是被拆开的大网格

- 主场景（FBO 366）2186 个 draw 里按 (program, tex0, tex1, 索引数, 顶点数, blend) 只有 **754 种**不同的网格；235 组有重复，覆盖 1667 个 draw。
- 最大的三组：纹理 469 / 470 / 471，各 **84 次**，索引 54 / 24 / 54，顶点 36 / 10 / 24。
- 每组 84 个 draw 之间，192 行顶点常量只有 **16 行**取值不同：96-99 和 104-109（每个 draw 都不一样，109 行有 71 种），116-121 偶尔变（2-3 种）。其余 176 行在这 84 次里完全一样。（`mesh_dupes.py`）
- 重放里对这三组各取 6 个 draw 比较顶点和索引的哈希（`rd_meshhash.py`，共 18 个）：469 与 470 组的 6 个**字节完全相同**（第 6 个取自帧里很靠后的位置），471 组索引相同、顶点 5 个相同 1 个不同。只验证了这 18 个，其余 736 种没有逐个验证。

结论：同一个墙段/路缘/窗框模块用同一张通用纹理画了很多次，每次带不同的摆放矩阵。这是 Xbox 版（以及 GC 版，同一引擎）模块化场景的做法，在 Xbox GPU 上提交一个 draw 几乎免费，所以 EA 没有动机去合并。**之前"建筑被一个 quad 一个 quad 拼出来"的说法不准确**（docs/07 和 docs/09 里也有这样的表述）：多数是重复的小模块；另有 1388 个主场景 draw 索引数 < 50（中位数 21 个索引、10 个顶点），其中单个 quad 117 个、单个三角形 15 个。

### 9.5 按"同网格同状态合成一个实例化 draw"估算还能剩多少

`instancing_potential.py`（key = FBO、program、4 个纹理、blend 状态、深度状态、索引数、顶点数）：

| 段 | draw | 同网格全部合并后 | 省 | 只合并相邻重复 | 省 |
|---|---|---|---|---|---|
| A 环境/反射 pass | 161 | 129 | 20% | 130 | 19% |
| B 世界不透明 | 1414 | 493 | 65% | 610 | 57% |
| C 世界半透明 | 207 | 65 | 69% | 85 | 59% |
| D 车 | 157 | 128 | 18% | 145 | 8% |
| E 半透明 | 152 | 41 | 73% | 52 | 66% |
| F 后处理 | 53 | 5 | 91% | 8 | 85% |
| G HUD | 256 | 27 | 89% | 46 | 82% |
| 合计 | 2400 | **888** | **63%** | **1076** | **55%** |

- 车的部件几乎都是不同网格，实例化帮不上；世界不透明几何是大头。
- 这是 draw 数的估算，**不是时间**：真机每个 draw 的提交约 20 us（§3.1），2400 -> 1076 理论上省 26 ms 左右（GL 线程 119 ms 的 22%），没有在真机上验证过。
- 旧方案（docs/09，每顶点选常量块）和"CPU 拼顶点"都是为"一个大网格被拆碎"设计的，方向不对；对重复模块应该用实例化，每实例只需约 10 个 vec4（160 字节）。

### 9.6 没做完的、不确定的

- 帧尾 537 个 draw（HUD、半透明、车的一部分）的 `Samples Passed` / `GPU Duration` 在 llvmpipe 回放里是无效值（`2^64-1` / NaN），原因没查到；像素数只在前 1863 个 draw 上有效，所以**没有"哪类物体占多少片元"的分类数据**，只有 draw 数和顶点数。
- 另外一个口径要注意：`draw_anatomy.py` 里按 draw 序号硬划的段（B/C/D/E/G）是这一个抓帧的边界，换一帧要重新划。
- 没有 NFSU2 PC 原版的 draw 数；"PC 版资源本来就是合并过的"这个猜想无法用现有数据验证。
- reVC 对比：re3-sdl 的 5167 个提交里没有任何降 draw call 的工作；它们在同一块 Mali 上是 217-440 个 draw/帧，结论是应用侧到顶、只有纹理图集能再降，所以没做（re3-sdl docs/08 §4、§6）。NFSU2 每帧 2200-2500 个 draw，是它的 5-10 倍。

### 9.7 下一步的假设

资源侧的"运行时烘焙"（场景分区加载时把静态实例合成世界坐标的大网格）成立的前提是**这些实例的摆放矩阵逐帧不变**。要先测：同一实例（网格 + 常量 96-109 行）在相邻帧、镜头移动时的哈希是否不变。静态比例高才值得做；低就改走实例化（每帧提交时合并）。
