# 10 - draw 合并重做：基线与方案

> 日期：2026-10-08。前置：[09 碎片 draw 合并尝试](09-碎片draw合并尝试.md)（旧方案，已回退）、[07 RenderDoc 帧捕获分析](07-RenderDoc帧捕获分析.md)。

## 1. 为什么回退旧方案

旧方案（提交 6dbb731）在顶点着色器里按 `gl_VertexID` 选常量块：每个顶点跑一个循环，再动态索引 `c[blk*192+i]`。PC 上 draw 减 76%、画面正确，R36S 上从 7-13 fps 掉到 0.2-2.5 fps。问题在方案本身：

- 改的是 shader，代价在 Mali 上完全不同于 llvmpipe，PC 验证不能推断真机；
- Mali 的 uniform 预算只够 5 块，合并率 1.45（PC 4.2），省不下多少；
- 每个 draw 都做 `mg_match`/`vertex_runs` 扫描，合并不成功时纯亏 CPU。

代码已 revert，`docs/09` 留作失败分析。默认行为不变（回退前后基线一致，见下）。

## 2. 基线（PC，llvmpipe，回退后）

工具：`RECOMP_PERF_LOG=2` 每帧一行 `[frame] n ms gl wait swap dc frag calls`，与 `[AUTOTEST] HUD live` 在同一日志流里，可以并排看比赛开始前后。`frag` = 索引数 < 50 的 draw。

```bash
BIN=$PWD/build/linux-hud/nfsu2_recomp HUD_STOP=12 RECOMP_SKIP_INTRO=1 \
  RECOMP_PERF_LOG=2 bash tools/pc/run.sh base 150
```

HUD 首次更新后各阶段（`build/base0`，每帧中位数）：

| 阶段 | 帧 | dc | frag | calls | ms |
|---|---|---|---|---|---|
| HUD 已创建，仍是加载/菜单画面 | 0-59 | 161 | 161 | 1542 | 38.7 |
| 赛前场景 | 80-209 | 1067 | 557 | 11729 | 40.2 |
| **比赛** | 225+ | **2531** | **1475** | **25621** | 44.1 |

要点：

- HUD 在 3D 场景出现前约 70 帧就开始更新（Player 构造时创建 HUD），所以 `HUD live` 是"进比赛流程"，稳态基线要从它之后约 220 帧起取。
- 比赛里 **58% 的 draw 是碎片**，平均每个 draw 约 10 次 GL 调用。
- `wait=0.0`：llvmpipe 下 GL 线程一直满载，PC 上看不出游戏线程是不是瓶颈。

## 3. R36S 基线（真机，2026-10-09）

```bash
R36S_HOST=192.168.10.241 python3 r36s/autotest.py --baseline   # 部署 + 进比赛 + 取数 + 热键退出
```

driver 的 `baseline` 模式：启动游戏，临时给 env.txt 加 `RECOMP_PAD_MASH=200,100,7` 和 `RECOMP_PERF_LOG=2`（跑完还原），等日志出现 `HUD live`，再收 420 帧 `[frame]`，在设备上汇总后 SELECT+START 退出。**菜单操作和 PC 完全相同**（游戏进程内连按，不再由 driver 通过 evdev 点 A）。进比赛 22.8 s，整个流程 80 s。

设备环境：`env.txt` 里 `RECOMP_GL_SKIP=320x240,128x128`（路面反射和车体环境贴图关闭），CPU 被限到 1200 MHz，结束时温度 72 C。

稳态（HUD 后第 335 帧起的 100 帧，中位数）：

| 指标 | 值 |
|---|---|
| 帧时间 | **125.2 ms**（约 8 fps，范围 106-236） |
| GL 线程忙 | 123.8 ms |
| WAIT（GL 等游戏线程） | 0.0 ms |
| draw / 碎片 draw | 2301 / 1430（**62%**） |
| GL 调用 | 15864（约 6.9 次/draw） |

30 帧窗口（HUD 后）：加载画面 161 draw、帧时间 45 ms，其中 WAIT 约 35 ms（游戏线程慢）；第 90 帧起 3D 场景出现，`WAIT` 降到 0，GL 线程满载；约第 240 帧后进入稳态。

结论与限制：

- 比赛里 GL 线程满载（`WAIT`=0），菜单/加载阶段则是游戏线程慢（`WAIT` 约 35 ms）。
- `GL` 是"帧时间 - WAIT - SWAP"，包含 GL 线程在驱动里等 GPU 的时间，所以单看它分不清提交开销和 GPU 负载。下一节用实验拆开。
- 取样要按场景，不能按帧号：HUD 出现后依次是加载（约 160 draw）、赛前场景（非碎片 draw 约 290）、比赛场景（约 870），各段时长每次不同。driver 现在以"非碎片 draw ≥ 600"判定比赛场景，跳过前 120 帧（比赛场景开头约 100 帧更重：dc 2300 -> 2670 -> 2290，帧时间 125 -> 170 -> 122 ms），再取 100 帧。（早期用"最后 100 帧"的两次结果，有一次落在赛前场景，那一次和随后的 dropfrag 对比无效。）

## 3.1 拆分实验（真机，比赛场景稳态，中位数）

开关在 `nv2a_gl.c`（只用于实验，会改画面）：`RECOMP_GL_EXP_DROPFRAG=1` 跳过索引 < 50 的 draw；`RECOMP_GL_EXP_RD=2` 每个 draw 周围开 `GL_RASTERIZER_DISCARD`（顶点和提交都在，片元全无）；`RECOMP_GL_EXP_RD=1` 是对照（只多两个调用）。

```bash
R36S_HOST=192.168.10.241 r36s/exp.sh base dropfrag:RECOMP_GL_EXP_DROPFRAG=1 \
    rd:RECOMP_GL_EXP_RD=2 both:RECOMP_GL_EXP_DROPFRAG=1,RECOMP_GL_EXP_RD=2
```

| 实验 | 帧时间 | GL 线程忙 | WAIT | draw | GL 调用 |
|---|---|---|---|---|---|
| base（4 次：123.8 / 125.2 / 120.0(对照) / 123.3） | 123.3 | **121.7** | 0 | 2214 | 15325 |
| 去碎片 draw | 103.9 | 59.9 | 45.0 | 846 | 6473 |
| 关光栅化 | 103.3 | 59.4 | 42.0 | 2222 | 19855 |
| 两者都做 | 111.9 | **32.4** | 78.1 | 869 | 8292 |

按 `GL = 固定 + 每 draw 提交 × draw 数 + 片元` 解：

- 关光栅化后留下的是固定 + 提交：59.4（全部 draw）与 32.4（只剩 846 个）之差 27 ms 来自 1368 个碎片 draw，约 **20 us/draw**。
- 固定部分约 **16 ms**（清屏、拷贝、present、队列）。
- 提交总计 20 us × 2214 ≈ **44 ms**，其中碎片 draw 占约 27 ms。
- 片元（光栅化）= 122 - 16 - 44 ≈ **62 ms**，其中碎片 draw 约 35 ms，其余 27 ms。

所以 122 ms 的 GL 线程帧约为：固定 16 + 提交 44 + 片元 62。这是线性模型，`rd` 多出的两个调用约 1-3 ms（对照组 120.0 与基线 123.8 无显著差异）。

**上限分析**：

- 合并碎片 draw 最多省提交 ~27 ms（实际约 20 ms），GL 线程 122 -> ~100 ms。
- 但后两组 `WAIT` 为 42-78 ms，GL 线程已经在等：**上游（游戏线程 + 执行器）每帧约 104-112 ms**，是下一个下限。合并 draw 的帧时间收益上限是 123 -> 约 105-110 ms（约 -12%），再往下要动上游。
- 片元 62 ms 是 GL 线程里最大的一块，合并 draw 碰不到。
- 去碎片 draw 的截图：路面变黑、HUD/路灯/招牌消失，车和大楼还在。路面和 HUD 就是被拼成碎片的。

## 4. 方案候选与优先级

按上面的拆分重排：

| # | 方向 | 对 GL 线程 | 说明 |
|---|---|---|---|
| 1 | 找出 62 ms 片元里谁最贵 | 最大一块 | 按 surface/pass 分别开关光栅化（每个 pass 一次实验），找出后处理、半透明、路面等的成本；分辨率/pass 裁剪不动 shader |
| 2 | 上游 ~105-110 ms | 决定下限 | GL 线程降到 100 以下之后，帧时间由游戏线程 + 执行器决定（docs/04 §8）。不动它，其他优化的收益被封顶 |
| 3 | 合并碎片 draw | 最多 -20 ms | 先做不改 shader 的版本（相同常量的相邻 draw，或 CPU 预变换）；改 shader 的方案必须先在真机验证 |
| 4 | 减冗余 GL 调用 | 小 | 比赛里 15k 调用 / 2.2k draw ≈ 7 次/draw，提交 20 us/draw，值得统计但上限有限 |

下一步先做 1（实验成本最低，收益最大），并同时看上游为何是 105 ms。
